- R3.2 und EK4: Einstufung und Rang zählen nur unter den Sorten, die Säen zeigt, also nur unter vorrätigen (siehe A9).

## Ziel

Im Detail einer Sorte unter «Saatgut» setzt Tim mit «Kein Saatgut mehr» die Sorte auf «Aufgebraucht». Säen zeigt sie danach nicht mehr, und im Saatgut-Manager steht sie unter dem Filter «Aufgebraucht». «Wieder vorrätig» oder eine neue Packung holt sie zurück. Packungen, Fotos, Keimrate und Verlauf bleiben erhalten, nichts wird gelöscht.

## Migration

Ja, additiv: eine neue Tabelle, keine bestehende Tabelle, Sicht oder Funktion ändert sich. Datei `supabase/migrations/20261113130000_vorrat_ereignis.sql` (neuer als `20261113120000_tuetenfoto.sql`). Label `db-lock`; zurzeit ist kein Pull Request offen. Die Dev-Migration läuft über `dev-migration.yml` vor Abnahme 1. Die Produktion gibt der Lead nach dem Lauf auf `hydrovisor-dev` und mit grünem Backup frei (Entscheid 0024); `deploy.yml` migriert vor dem Pages-Deploy.

- **Tabelle** `public.vorrat_ereignis` (A1, A2):
  - `id uuid primary key default gen_random_uuid()`
  - `client_id uuid not null unique`
  - `sorte_id uuid not null references public.sorte_schluessel (id)`
  - `saatgut_id uuid references public.saatgut (id)` (optional, A3)
  - `typ text not null check (typ in ('aufgebraucht', 'vorraetig'))`
  - `gilt_ab timestamptz not null`
  - `client_zeit timestamptz`
  - `nacherfasst boolean generated always as (erfasst_am - gilt_ab > interval '2 hours') stored`
  - `erfasst_am timestamptz not null default now()`
  - `app_version text not null`
  - `storniert_am timestamptz`
  - `storno_grund public.storno_grund`
  - `ersetzt_id uuid references public.vorrat_ereignis (id) on delete set null`

  Die Spalten folgen Konzept 8.1 Regel 3 wie `aufschub`, aber ohne `datenart` (A4). Kommentare stehen auf Tabelle und Spalten: Zweck, Plan 215, «es gilt das jüngste nicht stornierte Ereignis bis jetzt; eine danach erfasste Packung macht wieder vorrätig; die App löscht nie».
- **Index** `vorrat_ereignis_sorte` auf `(sorte_id) where storniert_am is null`. Kein Unique je Sorte: Jede Handlung ist eine neue Zeile.
- **RLS (8.1 Regel 6)** wie `20261113120000_tuetenfoto.sql` Abschnitt 2: `enable row level security`; `tim_lesen` (select), `tim_einfuegen` (insert with check), `tim_aendern` (update using und with check), je `to authenticated` mit `(select public.ist_tim())`, je mit `drop policy if exists` davor. Es gibt keine Delete-Policy und keine Policy `for all`.
- **Rechte** wie dort Abschnitt 3, ausdrücklich gesetzt (Plan 207 A17, Lehre aus #65):
  - zuerst `revoke all` von `anon`, `authenticated`, `service_role`;
  - `authenticated`: select, insert, update, delete (delete ohne Policy löscht 0 Zeilen);
  - `service_role`: select, insert, update;
  - `backup_leser`: select;
  - kein TRUNCATE.
- **Backup:** Rückfall E7 wie dort Abschnitt 4: Ein do-Block legt `backup_lesen ... for select to backup_leser using (true)` nur an, wenn `backup_leser` kein BYPASSRLS hat. Ein Backup-Skript mit eigener Tabellenliste gibt es nicht (geprüft: `scripts/`, `backup.yml` zählen nur Fotos). `00_zugriff.test.sql`, `11_backup.test.sql` und `12_tabellenrechte.test.sql` nehmen die Tabelle über ihre Schleifen von selbst auf.
- **Rückweg:** In einer Folgemigration `drop table public.vorrat_ereignis`, nur solange die Tabelle leer ist; mit Daten bleibt sie stehen (ein alter Client liest sie nicht).

## Domäne und Datenfluss (Signaturen)

**`src/domain/sorten/vorrat.ts`** (rein, G1):
- `type VorratTyp = 'aufgebraucht' | 'vorraetig'`.
- `interface VorratEreignisZeile { id; client_id; sorte_id; saatgut_id: string | null; typ: VorratTyp | string; gilt_ab: string; erfasst_am: string; storniert_am: string | null }`.
- `interface PackungZeit { sorte_id: string; erfasst_am: string; storniert_am: string | null }` (Ausschnitt einer Zeile `saatgut`).
- `interface VorratStand { vorraetig: boolean; seit?: string }`. `seit` ist `gilt_ab` des massgebenden «aufgebraucht», nur bei `vorraetig: false`.
- `vorratStand(ereignisse: readonly VorratEreignisZeile[], packungen: readonly PackungZeit[], sorteId: string, jetzt: Date): VorratStand`:
  1. Kandidaten sind die Ereignisse der Sorte mit `storniert_am === null` und `gilt_ab ≤ jetzt`.
  2. Ohne Kandidat gilt `vorraetig: true`.
  3. Sonst gilt das jüngste Ereignis: zuerst nach `gilt_ab`, bei Gleichstand nach `erfasst_am`, dann nach der grösseren `id`; verglichen wird auf die Mikrosekunde wie `juenger()` in `tuetenfoto.ts` (Plan 207 A6). Ist es «vorraetig», gilt `vorraetig: true`.
  4. Ist es «aufgebraucht», gilt `vorraetig: true` nur, wenn eine nicht stornierte Packung der Sorte mit `erfasst_am` nach dem `erfasst_am` dieses Ereignisses und `erfasst_am ≤ jetzt` besteht (A5). Sonst gilt `{ vorraetig: false, seit: gilt_ab }`.
- `vorratAus(t: Teile, sorteId: string, jetzt: Date): VorratStand`: liest `t['vorrat_ereignis']` und `t['saatgut']`; fehlt ein Teil, gilt er als leer.
- `vorratVerlauf(ereignisse, sorteId, jetzt): { typ: VorratTyp; giltAb: string }[]`: nicht stornierte Ereignisse der Sorte bis `jetzt`, das jüngste zuerst (gleiche Ordnung wie oben).
- `vorratVorgang(e: { sorteId: string; typ: VorratTyp; clientId: string; jetzt: Date }): Schritt[]`: genau ein Schritt `{ art: 'neu', tabelle: 'vorrat_ereignis', felder: { client_id, sorte_id, saatgut_id: null, typ, gilt_ab: jetzt.toISOString() } }`. `gilt_ab` steht ausdrücklich im Vorgang, damit ein wiederholtes Senden dieselbe Zeile ergibt und nicht «abweichend» meldet (TO2; Muster `abhakliste/vorgaenge.ts`). `client_zeit` setzt `zeileVorbereiten()`.

**`src/domain/sorten/saatgut.ts`:**
- `type SaatgutStatus = 'vollständig' | 'Recherche offen' | 'aufgebraucht'`.
- `SaatgutZeile` erhält `aufgebraucht: boolean`. Bei aufgebrauchten Sorten ist `status` gleich «aufgebraucht»; `vollstaendig`, `ohneFoto` und `fotoPfad` bleiben wie bisher berechnet.
- `saatgutListe(t: Teile, jetzt?: Date)`: je Sorte `vorratAus(t, sorteId, jetzt ?? OHNE_GRENZE)`. `OHNE_GRENZE` ist eine Konstante `new Date(8.64e15)`, also ohne obere Zeitgrenze, damit alte Aufrufe gültig bleiben (A7). Die Oberfläche übergibt immer `jetzt()`.
- `type SaatgutFilter = 'vorraetig' | 'ohne_foto' | 'aufgebraucht'`. Was jeder Filter zeigt:
  - `vorraetig`: Sorten mit `!aufgebraucht`;
  - `ohne_foto`: Sorten mit `!aufgebraucht && ohneFoto`;
  - `aufgebraucht`: Sorten mit `aufgebraucht`.
- `saatgutZahlen(liste): { vorraetig; ohneFoto; aufgebraucht }` nach denselben Filtern.
- `nachtragReihe(liste)`: nur Sorten mit `!aufgebraucht && ohneFoto`. `nachtragStarten()` übernimmt das.

**`src/domain/pflanzung/saeen.ts`:**
- `sortenAuswahl(teile: Teile, jetzt?: Date): SorteWahl[]` behält nur Sorten mit `vorratAus(teile, id, jetzt ?? OHNE_GRENZE).vorraetig`. «Wie letztes Mal» kommt nur dann an den Anfang, wenn diese Sorte vorrätig ist.
- `passungVon(teile, e, s, jetzt, zeitzone)` ruft `sortenAuswahl(teile, jetzt)` auf, damit der Rang beim Speichern unter denselben Sorten zählt, die Säen zeigt (R3.2, EK4).

**Schreibweg:** Die Karte ruft `vorratVorgang({ sorteId, typ, clientId: neueClientId(), jetzt: jetzt() })` auf, dann `vorratSenden(vorgang)`, das intern `schreiben(vorgang, { jetzt, zeitzone })` aufruft. Danach lädt das Bündel nach (`beiErfolg`), und `vorratAus()` liefert den neuen Stand. `vorratSenden(vorgang): Promise<'gespeichert' | { meldung: string; wiederholbar: boolean }>` meldet bei «abweichend» «Nicht gespeichert: Diese Angabe ist schon anders gespeichert.», nicht wiederholbar; sonst gibt es den Text aus dem Schreibergebnis zurück, wiederholbar.

**Datenfluss:** `schreiben()` → `vorrat_ereignis` → Bündel (IndexedDB, offline) → `vorratAus()` / `saatgutListe()` / `sortenAuswahl()` → Sorte-Detail, Saatgut-Liste, Säen Schritt 1.

## Risiken

| Risiko | Folge | Gegenmassnahme |
|---|---|---|
| Typen nicht neu erzeugt | Typecheck scheitert am Abgleich `Erfassungstabelle` gegen die Tabellen mit `client_id` (`schreiben.ts` Z. 63), Typen-Abgleich E6 rot | `supabase db reset`, dann `supabase gen types typescript --local > src/daten/datenbank.types.ts` im selben Commit wie die Migration |
| Vorschau ohne Dev-Migration | Bündel lädt `vorrat_ereignis` nicht, Abnahme 1 scheitert | `gh workflow run dev-migration.yml` nach dem Push und vor Abnahme 1 |
| Abnahme 1 und E2E lassen Sorten aufgebraucht zurück | Säen zeigt in `hydrovisor-dev` bzw. lokal eine Sorte nicht; die Tests anderer Pakete schwanken | E2E setzen im `finally` zurück (A14); der Lead tippt nach Abnahme 1 «Wieder vorrätig»; keine Datenart, `datenart_loeschen` räumt nicht (A4) |
| Uhren: `gilt_ab` vom Gerät, `erfasst_am` vom Server | Eine falsche Gerätezeit verschiebt «bis jetzt» | Packungsregel vergleicht nur Serverzeiten (`erfasst_am`, A5); das Gerät hat Netzzeit; Nachfassung über `nacherfasst` sichtbar |
| Rang beim Säen ändert sich | `pflanzung.rang` (EK4) zählt nur unter vorrätigen Sorten | gewollt: Rang = Position in der gezeigten Liste; `passungVon()` und die Liste nutzen denselben Filter (A9) |
| Doppeltipp auf «Kein Saatgut mehr» | zwei Ereignisse | Knopf gesperrt, bis das Bündel den neuen Stand zeigt; zwei gleiche Ereignisse ändern den Stand ohnehin nicht |
| Optionales `jetzt` | Ein neuer Aufrufer vergisst `jetzt` und zählt künftige Ereignisse mit | Oberfläche übergibt immer `jetzt()`; der Prüfer prüft alle Aufrufer; künftige Ereignisse schreibt die App nicht (kein Rückdatieren nach vorn) |
| `db-lock` | ein zweiter offener PR mit Migration wird blockiert | Label setzen; vor dem Push `gh pr list` prüfen (heute keiner offen) |
| Drei Filter auf 360 dp | Umbruch statt einer Zeile | `Choice` bricht zwischen Optionen um, nie im Wort; AK7 prüft nur «kein waagrechtes Scrollen» |

## Nicht-Ziele

- Ereignis je Packung in der Maske (`saatgut_id` bleibt `null`), Bestand oder Verbrauch zählen.
- SQL-Sicht `v_vorrat` und Push-Hinweise wie «Saatgut fast leer».
- Stornieren eines Vorrat-Ereignisses in der Oberfläche (Korrektur ist «Wieder vorrätig»; Storno bleibt für Fehlerfassungen über den Schreibweg).
- «Satz duplizieren» (R11.1) mit einer aufgebrauchten Sorte sperren oder warnen; Keimung, Umsetzen, Pflanze und Verlauf der Pflanzungen ändern sich nicht.
- Endgültiges Löschen einer Sorte oder Packung (8.1 Regel 3).
- Änderung von `sortenListe()`, `sortenDetail()`, `sorteDetail()` (Domäne), `datenart_loeschen()`, Seed, Demo, Backup, Edge Functions, `design-system/`.
- Nachführung des Konzepts selbst (nur Posten in `pakete.md` I3) und des Entwurfs `docs/spec/02_datenmodell.sql`.
- Alles an der Anlagen-Übersicht (N4).

## Annahmen (A)

1. **Name `vorrat_ereignis`** (Vorgabe des Leads, beibehalten): fachlich deutsch ohne Umlaute; das Suffix zeigt, dass jede Zeile eine Handlung ist. Bewusst nicht `ereignis_vorrat`, weil die Bündelteile `ereignis_platz`, `ereignis_satz` und `ereignis_pflanzung` Ausschnitte der Tabelle `ereignis` sind. Verworfen wurde auch, zwei neue Typen in `ereignis` mit `sorte_id` anzulegen (Spalte besteht): Issue und VR1-AK1 verlangen eine eigene Tabelle mit eigener Prüfung der Art, und neue Werte in `ereignis_typ` wären in der Migration nicht in derselben Transaktion nutzbar.
2. **Zeitachse nach Konzept 8.1 Regel 3 statt `zeitpunkt`** (Änderung der Vorgabe): Der fachliche Zeitpunkt heisst `gilt_ab`, dazu `client_zeit`, `nacherfasst`, `storno_grund` und `ersetzt_id` wie bei jeder Erfassungstabelle. Die Tabelle steht in `MIT_ZEITACHSE`, damit `zeileVorbereiten()` `client_zeit` setzt und ein Storno `storno_grund` sendet. Eine Spalte `gilt_ab` ausserhalb von `MIT_GILT_AB` würde `zeileVorbereiten()` entfernen. Preis: eine Zeile in `datenpfad-runde1.test.ts` (`size` 9 → 10). Mit der Vorgabe `zeitpunkt` entfiele diese Zeile; dann gälten Regel 2 («nach `gilt_ab`») und Regel 3 nur sinngemäss. Der Lead kann bei der Freigabe zurück auf `zeitpunkt` wechseln, ohne dass sich der übrige Plan ändert.
3. **Spalte `typ` statt `art`** (Änderung der Vorgabe): Im Saatgut-Kontext heisst «Art» die Pflanzenart (`art_id`, `art.name_de`, Auswahl «Art»); `typ` folgt `ereignis.typ`. «Die Art» in VR1-AK1 meint die Spalte `typ`. Werte `aufgebraucht` und `vorraetig` als `text` mit `check` wie `tuetenfoto.seite`, damit ein späterer Wert additiv bleibt. `saatgut_id` bleibt optional; es gibt keine Prüfung, ob die Packung zur Sorte gehört, weil die Maske sie nicht schreibt (Issue-Annahme 1).
4. **Keine Spalte `datenart`** (Vorgabe des Leads, passt): Das Ereignis gehört zur Sorte, und Sorten sind seit #199 echt; `saatgut` und `tuetenfoto` haben ebenfalls keine. Demo-Daten erzeugen keine Vorrat-Ereignisse; `datenart_loeschen()` und `npm run demo -- --loeschen` bleiben unverändert. G5 ist nicht berührt.
5. **Packung nach «aufgebraucht»:** Der Vergleich nutzt `saatgut.erfasst_am` gegen `vorrat_ereignis.erfasst_am`, beide Serverzeit, statt `gilt_ab` (Gerät); so stört eine abweichende Gerätezeit die Reihenfolge nicht. Die Packung muss nach dem Ereignis liegen (gleicher Zeitpunkt reicht nicht), nicht storniert sein und `erfasst_am ≤ jetzt` haben. Damit gilt Issue-Annahme 3 ohne weiteren Schritt und ohne neue Zeile.
6. Eine aufgebrauchte Sorte zeigt in der Liste nur das Wort «aufgebraucht» (kein « · ohne Foto» und kein «Recherche offen»), weil «Fotos nachtragen» und Recherche für sie nicht anstehen. Das Feld `vollstaendig` bleibt in der Zeile.
